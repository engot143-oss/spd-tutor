# SPD Tutor — product and implementation plan
Research checked: October 28, 2026 (Pacific). Scope: US-oriented independent educational prototype.

## Product and success criteria
A new sterile processing learner opens a public link, selects a chapter, studies a short concept, answers eight original questions, receives immediate source-linked explanations, and returns on the same browser/device to resume. No registration, installation, backend, analytics, AI calls, or student data sent to GitHub by application code. This is a 60-minute-style build scope, not a promise of certification readiness or a one-hour course.

MVP acceptance: one usable chapter; eight questions; answer submission locks each answer; score counts first submitted answers once; explanations and simpler wording; navigation to any question; completion and restart; persistent local progress; gracefully usable without storage; mobile layout and keyboard semantics; official optional ChatGPT links; independent-study and content-review notices. Future chapters must never imply available lessons or fabricated progress.

## Evidence and content boundaries
- [CDC cleaning](https://www.cdc.gov/infection-control/hcp/disinfection-sterilization/cleaning.html): prerequisite cleaning, soil removal, drying, friction/fluidics, mechanical cleaning. CDC web page dated November 28, 2023, presenting its 2008 guideline. It is foundational guidance, not a newly issued 2026 standard.
- [CDC recommendations](https://www.cdc.gov/infection-control/hcp/disinfection-sterilization/summary-recommendations.html): compatible agents, manufacturer instructions, inspection and classification. No universal cycle temperatures, chemical dilutions, or device-specific procedures in this demo.
- [CDC risk classification](https://www.cdc.gov/infection-control/hcp/disinfection-sterilization/rational-approach.html): critical items require sterility; semicritical items need at least high-level disinfection. Device IFUs, current standards and facility policy govern actual work.
- [HSPA CRCST overview](https://myhspa.org/certification/certification-overview/certified-registered-central-service-technician-crcst/) currently links [November 2023 revised outline](https://myhspa.org/wp-content/uploads/2024/01/HSPA_CRCST_Content_Outline_2023.Revision.pdf). Seven domains: departmental considerations 15%; cleaning/decontamination/disinfection 21%; preparation/packaging 21%; sterilization process 21%; sterile storage/transport/inventory 9%; patient care equipment/distribution 5%; professional development/human relations 8%. Total 100%. These are domain weights, not this demo's question distribution. Certification also requires hands-on experience; check HSPA directly for eligibility.
- [CBSPD technician page](https://www.cbspd.net/tech/) links the [November 2026 candidate bulletin](https://www.cbspd.net/wp-content/uploads/2026/10/Technician-CB-w-App-125-NOV-2026.pdf), outline on printed pages 9–10 (PDF pages 13–14). Different credential and blueprint; do not combine its weights with CRCST. Its eight domains are roles/responsibilities 13%; life science 9%; decontamination/disinfection 19%; preparation/handling 16%; sterilization 18%; sterile storage/inventory/distribution 11%; patient care equipment 6%; ethics 8% (total 100%). Recheck the official bulletin before any full certification track.

All demo questions, distractors, mini-lessons and explanations are newly authored. Source review here means editorial comparison with public CDC guidance by the builder, NOT independent clinical validation. A qualified SPD educator must review and sign off before promotion as a validated educational resource. No proprietary exam items, textbook excerpts, HSPA logos, or credential-provider endorsement. Do not reproduce paywalled AAMI/AORN standards. Link authorized resources instead.

## Open-source pattern inspection and decision
[James Q Quick's vanilla quiz project](https://github.com/jamesqquick/Build-A-Quiz-App-With-HTML-CSS-and-JavaScript), [MIT license](https://github.com/jamesqquick/Build-A-Quiz-App-With-HTML-CSS-and-JavaScript/blob/master/LICENSE), inspected repository structure and README. Its separate feedback, progress-bar, local-storage high-score, and local-question stages are suitable patterns. Adopt the concepts of question data separate from rendering and local browser persistence. Replace named leaderboards with anonymous chapter answers; replace automatic advancement with learner-controlled next; omit remote trivia APIs. No source code copied. Source-file inspection was unavailable: direct game.js retrieval failed, and the master-stage folder page returned a loading error. Therefore this comparison is limited to the verified README, folder structure and MIT license; no claim of an upstream code audit. Implementation is original. A framework/LMS is unnecessary for eight questions; no dependencies or install needed for students. Additional repository adoption is deferred rather than accepting unverified licenses.

## Architecture
Root index.html, styles.css, questions.js, app.js, .nojekyll and LICENSE. Classic deferred scripts and relative paths support GitHub project subpaths and direct-file preview; HTTP(S) is the supported persistence deployment. questions.js exposes a versioned content array (id, objective/topic, prompt, choices, correct answer index, explanation, simple explanation, source). app.js owns validated state and DOM rendering. No build step, fetch, cookies, third-party fonts, CDN scripts, forms submitting data, API keys, or server.

State key spd-tutor:v1; payload includes schema/content version, array of submitted answer indices/nulls, current question index, text size. Derive score from answers, never trust stored score. Validate exact array length, integer bounds and content version before restore. Invalid/old records fall back to new state with a message. Saving exceptions fall back to memory and explicitly announce session-only progress. One origin/browser/profile only; no cross-device sync, guaranteed backup, or recovery after clearing site data. Two tabs use last write wins; advise one tab. Reset only the app key with explicit inline confirmation; retain text preference in-session. No names or free-form patient information collected. Future schema changes require migration or a clear reset notice, never silently reinterpret old answers.

## Content roadmap and review process
1. Cleaning foundations (live): cleaning before treatment; drying soil; IFU-based washer operation; compatible detergent; critical items; semicritical items; friction; ultrasonic cleaning vs sterilization.
2. Preparation/packaging (planned): inspection, function, packaging selection and labels.
3. Sterilization (planned): modality selection, monitoring, documentation, failure escalation.
4. Storage/distribution (planned): package integrity, handling, inventory.
5. Safety/professional practice (planned): occupational safety, communication and quality.
Later split/expand to all seven CRCST domains; add a separately mapped CSPDT track only after review. Chapter cards are topic navigation, not a substitute for the official blueprint.

Each content change: record objective, authoritative URL/section, date checked, author, independent reviewer, rationale for correct answer and distractors, review status, content version. Recheck links and guidance before release and quarterly thereafter; review device/standard changes sooner. Report an issue via maintainer contact once a repository exists; never request real patient details. Retire outdated items and bump content version. No claims of CE credit, exam equivalence or pass prediction.

## UX and accessibility
Quiet ivory/navy/teal palette; spacious cards; system fonts; base 18px with saved larger-text option. Single main task, chapter sidebar on desktop and stacked mobile layout. Native radio group, fieldset/legend, explicit Check answer, live feedback and manually controlled Next. Jump to question buttons support targeted study. Unanswered items remain available after finishing other questions. Visible focus, skip link, semantic landmarks, text labels beyond color, large touch targets, wrapping layout at 320px, no timer or motion pressure. Completion gives numeric score and review navigation, not pass/fail. Aim WCAG 2.2 AA; browser checks are not full accessibility conformance certification. Human screen-reader and real iOS/Android checks remain release work.

## Optional ChatGPT path
Provide a selectable generic learning prompt and official https://chatgpt.com/ and https://chatgpt.com/download/ links. Learner manually copies the prompt; no prefilled query URL, automatic transfer or embedded AI. Label external service and privacy/account/availability differences. Ask for explanations with sources; discourage sharing patient/employer information and treating generated output as clinical instructions. Core quiz remains fully functional without AI.

## Privacy/security/hosting
Local storage contains only learning state, accessible to scripts on the same origin and to other users of that browser profile. App never sends answers to GitHub, but GitHub serving a website still receives ordinary requests/network metadata. External source/ChatGPT clicks contact those sites; use no-referrer links. No tracking or consent banner needed for nonexistent analytics, but present a plain-language storage notice and delete control. Static answers are public and inspectable; fine for practice, unsuitable for secured exams. Use CSP to restrict scripts/connects, no untrusted HTML insertion, no secrets. Hosting costs depend on GitHub terms; public-repo GitHub Free Pages is supported. [Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits): 1 GB published size and soft 100 GB/month bandwidth; not unlimited. Small static assets keep load low.

## 60-minute-style implementation sequence
0–12 research and scope; 12–20 architecture/content draft; 20–42 accessible UI and quiz state; 42–50 storage/fallback/privacy; 50–58 bounded verification; 58–60 handoff. These are planning allocations, not a measured elapsed-time claim. Drop extra chapters/animations/integrated AI before dropping correctness or privacy. This run builds the complete bounded MVP, with launch review listed separately.

## Focused verification (freeze at five checks)
1. Real browser quiz journey: wrong/right answers, no double scoring, skip/jump, completion 7/8, retry/reset.
2. Persistence: reload, malformed storage, unavailable storage, reset only this key.
3. Mobile/keyboard: 390px and 320px overflow, radio keyboard operation, focus after feedback, larger text; desktop visual inspection.
4. Content/contracts: eight unique ids, valid correct indices, sources, explanations, expected files and local asset links; syntax check.
5. Privacy/deployment: no application external requests, no API keys/dependencies, serve under project subpath and verify page/assets. No deployment claim from local tests.
Stop after passing checks. One focused fix/rerun per observed defect; prolonged diagnosis stops the build. Record exact observed outcomes in TEST-RESULTS.md. Not tested: broad browser matrix, physical devices, assistive technology, clinical validation, live Pages deployment/load.

MIT for original code and authored demo content; referenced organizations retain their own rights. No workflow dependencies required. This task prepares the project; it does not select an account, create/push a public repository or claim a live URL. Before public educational promotion: Eric's review, independent educator signoff, real-device/screen-reader checks, correct public contact and provenance, then verify deployed URL. Retain this demo label until review is complete.
